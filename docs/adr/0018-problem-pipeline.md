# 0018. Problem pipeline: validate before publishing, rejudge on a test-set version change

**Status:** Accepted (Phase 10), implemented on `feat/10-problem-pipeline`.

## Context
Problems are directories (`problem.yaml`, `statement.md`, `starters/`, `tests/`, `solutions/`). The test-set version is a content hash of the checker and every test (ADR 0005); the API upserts problems from disk at startup, submissions are stamped with the version at accept time, and runners fetch the bundle for exactly that version (ADR 0011). Nothing yet checked that a problem is well formed before it was published, and nothing happened to existing submissions when a test was fixed: they kept a verdict from the old tests forever. Three details of the existing design also blocked a rejudge: the verdict write was "first write wins" per submission id (Postgres `ON CONFLICT DO NOTHING`), the runner skipped any job whose submission already had a Redis verdict marker (`<prefix>:verdict:<id>`, 7 days), and the reaper and status watcher had to stay consistent with a submission going from judged back to queued.

## Decision
- **Validation is a judge subcommand in two steps.** `judge validate <problem-dir|problems>` (`judge/cmd/judge/validate.go`, logic in `judge/validate`) first runs structural checks that need no sandbox: slug equals the directory name, title, difficulty, limits within bounds (time at most 10 s, memory 16-1024 MB), tests are complete NAME.in/NAME.out pairs with no orphans, no names differing only by case, sizes (4 MiB per test file, 32 MiB in total, 3 to 200 tests), samples exist, at least one hidden test, and statement and starters present (warnings by default, failures with `-strict`, because `sample-sum` is a judged fixture with neither). Then the reference-solution check judges every `solutions/<lang>/<verdict>.<ext>` through the existing engine and requires that verdict (`ac` passes every test, `wa tle mle re ce ole` get theirs), and requires an `ac` solution per language that has solutions. The second step needs root, nsjail and cgroup v2 and refuses to start otherwise; `-structure-only` skips it. `make validate-problems` runs it for all problems.
- **The transition is explicit.** `store.SyncProblem` (`api/internal/store/rejudge.go`) reads the stored version under `FOR UPDATE` and upserts in one transaction, returning old and new version. Old bundles are never deleted from object storage: they are keyed by version, so submissions still on an old version stay judgeable.
- **Rejudge moves rows first, then enqueues.** `store.BeginRejudge` selects a problem's stale submissions (judged with a verdict for another version, or queued or judging against an older version), sets their `test_set_version` to the current one, `status` to `queued` and `enqueued_at` to NULL in a single statement (one transaction per batch of 100, `FOR UPDATE SKIP LOCKED`), and returns them with their source. `api/internal/rejudge` enqueues a job per row with the new version and calls `MarkEnqueued`. A row whose enqueue fails keeps `enqueued_at` NULL, so the existing reaper re-queues it with the new version; no new recovery path.
- **Triggers.** The API startup sync (`api/cmd/api/main.go`) rejudges every problem whose version changed, after bundles are published and the queue is open. `api/cmd/rejudge <slug>` (`-dry-run`, `-batch`) syncs one problem from the problems directory, publishes the bundle and rejudges on demand; it holds the database credentials like the API. Runners still never touch the database.
- **Verdict write: idempotent, but a rejudge may replace.** `RecordVerdict` stores a verdict only for the submission's own `test_set_version`; it replaces a stored verdict only when the incoming version equals the submission's current version and differs from the stored one. A redelivery of the same verdict, a conflicting verdict at the same version, and a late verdict from the old job are all no-ops. An `IE` verdict (dead letter, host failure) never replaces a real verdict, but returns a requeued submission to `judged` so a failed rejudge keeps the previous result instead of hanging.
- **Redis marker scoped to the version.** `queue.Publish` and `Published` key the verdict marker by submission id plus test-set version (id alone when the version is empty, as for `lfq` jobs). Without this the runner acknowledged a rejudge job as "already judged" and `Publish` dropped its result. The runner passes the job's version and its internal-error result now carries it.
- **Status and reaper.** The status watcher only moves `queued` to `judging`, so it works unchanged for a requeued row. The reaper only takes `queued` rows with `enqueued_at IS NULL`; rejudged rows are marked right after their enqueue, so it does not double-enqueue them, and picks up only the ones that failed.

## Alternatives
- **Rejudge only on an explicit command.** Safer against surprise load, but then a fixed test set silently leaves wrong verdicts until someone remembers; the exit criterion says the fix triggers the rejudge. The command exists too, for retries.
- **Enqueue first, then update the rows.** If the commit failed, the job would carry a version the row does not have and its verdict would be dropped. Moving rows first makes every failure fall back to the reaper.
- **A new `rejudge` column or table.** Not needed: comparing `submissions.test_set_version` and `verdicts.test_set_version` with the problem's version already says what is stale, and the comparison is naturally idempotent.
- **A verdict history table.** Keeping every verdict per submission would support audit, but acceptance, the submissions list and the SSE stream all read one verdict per submission; a second table is deferred until something needs it.
- **Running the reference check in the API or a runner.** The sandbox lives in the judge module and the check is an authoring-time step, so it is a CLI on the dev host (and later CI), not a service.
- **Replacing the Redis marker with a TTL shorter than any rejudge.** Fragile; the version in the key is exact.

## Consequences
- While a rejudge is pending, a submission is `queued` and still carries its old verdict row. Clients that show the verdict whenever one exists will show the old verdict until the new one lands; clients keyed on status see `queued`/`judging` again. Acceptance briefly counts old verdicts.
- A problem whose tests are broken back and forth is rejudged each time; each change costs one judging job per affected submission. Batches of 100 bound the transaction size, not the queue size.
- Rows left stale by a failed rejudge (a runner IE keeps the old verdict at the old version) are selected again by the next startup sync or `rejudge <slug>`, which retries them.
- An `lfq` job with no version and a published result with a computed version use different marker keys, so a redelivered tool job may be judged twice; `Publish` still records one result. Real submissions always carry a version.
- Not measured here: rejudge throughput and the extra startup time of a large rejudge, which runs before the API starts listening.
