### Unit 4: `feat/5-sse-status` (2026-10-02)
Design (Claude): the handler polls Postgres every 500 ms and emits only changes, instead of an in-process pub/sub hub. The database is the one source of truth, so this works unchanged with several API instances (a hub would only reach clients on the instance that processed the event). Cost: a primary-key read per open stream every 500 ms; bounded by a cap of 200 streams per instance. Latency is one poll interval plus the status watcher's read.
1. Claude (repo): `api/internal/server/events.go`, route `GET /submissions/:id/events`. Behaviour: 404 JSON for an unknown id (before any stream headers); the first event is the current state; `event: status` with `{"status":"queued"}` / `{"status":"judging"}` on each change; `event: verdict` with the same view as `GET /submissions/:id` (`{"status":"judged","verdict":{...}}`) and the stream ends; a `retry: 3000` hint; a `: keep-alive` comment every 15 s; `event: timeout` after 10 min; `event: error` after 10 consecutive failed reads (with a generic message, the cause goes to the log); 503 with `Retry-After` beyond 200 open streams; `X-Accel-Buffering: no`. A client that connects after the verdict gets it at once with no polling. No dependence on `Last-Event-ID`: state, not history, is streamed.
2. Claude (repo): `api/internal/server/events_test.go` (10 tests, run with `-race` locally): full flow and no duplicate events, no hidden data in any event (banned substrings: version, `test_set_version`, `source`, `stderr`, `expected`, `input`), late client, unknown id, transient and repeated read errors (and the error text `secret-host` never appears in the stream), time limit, heartbeats, stream cap and slot release on disconnect.
